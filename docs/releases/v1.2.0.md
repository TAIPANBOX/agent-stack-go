# agent-stack-go 1.2.0

Writers that share one event stream keep one chain. Before this release, two
writers appending to one file on a shared volume could each overwrite the
other's lines, and the verifier reported no break, because the surviving
writer's chain was consistent with itself. No exported identifier moved:
`scripts/api-surface.sh` holds `api/surface.txt` at its 143 declarations.

The minor bump is not for the API. A writer can now return an error it never
returned before (see "Behaviour a consumer can notice"), and a consumer should
be able to see that from the version alone.

## Fixed (agent-stack-go#75): writers sharing one stream keep one chain

- **`event.ChainedWriter` stamps `prev_hash` from the file, under an exclusive
  `flock(2)` on the file held until the line is appended.** Every `Write` takes
  the lock, reads the last line on disk, stamps `prev_hash` from it, appends and
  unlocks. Before this, a writer chained from the hash of its own previous
  write, held in memory. That is right only while it is the file's only writer,
  and the shared events bus does not guarantee that: a pod being replaced keeps
  appending through its grace period while its successor has resumed the chain,
  and a service and its CronJob can share one stream.
- A stream whose last byte is not a newline (a writer killed mid-line) gets one
  before the next event, so the event starts a fresh chain after the fragment:
  a restart, not a break.
- The last line is found by reading backwards from the end of the file, up to
  VerifyChain's own 4 MiB line cap (it was a fixed 1 MiB window).
- Invariant 27 in `CLAUDE.md` and thirteen scenarios in
  `features/chained-writer-lock.feature`, each bound to a test. Fourteen new
  tests; eleven of them went red on the unfixed writer.

## Measured on a shared volume (2026-10-14)

Two writers, each appending 10,000 events with one `Write` per event, to one
1 GiB `ReadWriteMany` volume (Longhorn, NFS 4.1, `local_lock=none`). Each
writer ran on its own node of a five-node k3s lab cluster. The file was read
back from both nodes and verified with `event.VerifyChain`.

| Writer | Run | Events appended | Lines in file | Chain breaks |
|---|---|---|---|---|
| before this change (fd366a4) | 1 | 20,000 | 10,000 | 0 |
| before this change (fd366a4) | 2 | 20,000 | 10,000 | 0 |
| this release (fa6f94b) | 1 | 20,000 | 20,000 | 0 |
| this release (fa6f94b) | 2 | 20,000 | 20,000 | 0 |

- Before this change, half of the events were missing from the file in both
  runs, and no write returned an error.
- With this change, both runs hold all 20,000 events, one chain, and the same
  SHA-256 when read from either node.
- Cost: a lone writer on the locked path took 16.8 ms per append over the NFS
  volume (1,000 events), which is the NFS round trips made under the lock. The
  unlocked writer took 35 to 37 microseconds per write on the same volume.
- Hand-over between the two writers is not fair. In one run the file holds four
  runs of one writer, and in the other one writer waited about 2.5 minutes
  while the other appended.

## Behaviour a consumer can notice

- `NewChainedWriter` fails when the file cannot be locked at all. Before, it
  opened the file and wrote regardless.
- `Write` returns an error and appends nothing when the lock cannot be taken or
  the end of the file cannot be read. An error from releasing the lock is
  returned although the line is already on disk.
- `Write` blocks while another writer of the same file holds the lock, for as
  long as that writer's append takes.
- `ResumedFrom` still reports what the file held at open. It is no longer the
  value the next `Write` chains from, because every `Write` reads the file.
- On Windows there is no cross-process lock, only the re-read of the tail. No
  bus runs there.

## Upgrade notes

- No code change for a consumer: no exported identifier changed. A service
  that appends to a stream another process also appends to (on a shared bus,
  any service whose pod can be replaced, or a service that shares a stream with
  its CronJob) should move to this version to stop false `chain_broken`
  reports.
- Pin a released tag. The verifier image is
  `ghcr.io/taipanbox/agent-conform:v1.2.0`; there is no `latest`.
- Release asset names still carry no version (`agent-conform_<os>_<arch>`), so
  `releases/latest/download/<name>` links keep resolving.

## Not proven

- Durability: `Write` does not fsync, as before. A line written just before the
  host loses power may be lost. The next writer chains from whatever is last on
  disk, so the chain does not break.
- The NFS behaviour was measured on one storage stack, described above. Mounts
  with `local_lock=flock` or `local_lock=all`, and other network filesystems,
  keep the lock on one node only. A mount that refuses `flock` now makes
  `NewChainedWriter` fail, which is the intended loud failure.
- The two-writer harness is not in this repository. The measurement cannot be
  rerun from the repository alone.
- Not measured: a node, the share manager or the network failing mid-run;
  fairness under more than two writers; the `watch-dir` verifier reading while
  writers append.
- A writer that bypasses this library (another language, or a shell `>>`) is
  not excluded. Other services in the estate that keep the same in-memory chain
  need their own fix; they are not changed by this release.
- `event.Writer` (the unchained writer) still appends without a lock. Two nodes
  appending to one NFS file through it can overwrite each other's lines.
- The 1.2.0 image and the release archives are built and signed by
  `release.yml` on the tag. Their digests are not recorded in these notes.
